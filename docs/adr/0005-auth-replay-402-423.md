# ADR-0005: Treat 402 and 423 like 401 for token refresh and replay

## Context

iiko's error reference says `402 Payment Required` and `423 Locked` mean the same as `401`: the
API key, license or subscription is blocked. It tells integrations to obtain a new token once and
replay the request. The SDK mapped only 401 and 403 to `IikoAuthError` and replayed only 401, so
402 and 423 surfaced as a generic `IikoApiError` and were never retried.

## Decision

- `IikoAuthError` covers 401, 402, 403 and 423 from the API and the token endpoint.
- The API replay — invalidate the token, fetch a new one, resend once — triggers on 401, 402 and
  423.
- 403 stays an `IikoAuthError` but is not replayed: iiko treats it as an access or request error,
  and another token cannot fix it.
- 401, 402 or 423 from `/api/v2/access_token` are not replayed: the token request already failed,
  so there is nothing to resend.
- At most one replay. If it is rejected, the error propagates.

## Consequences

- A 402 or 423 now causes one extra token request and one extra API call, as iiko documents.
- The class change is source-compatible for consumers catching `IikoApiError`, but code that
  distinguished 402/423 as generic API errors now sees `IikoAuthError`.
- A second auth error is not replayed, so a blocked key cannot turn into a retry loop.
- The 5xx, network and timeout policy is unchanged: see ADR-0002 and ADR-0003.
